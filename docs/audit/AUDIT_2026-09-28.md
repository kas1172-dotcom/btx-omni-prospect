# BTX Omni Prospect — Engineering Audit of the Master Rebuild Plan

**Date:** 2026-09-04
**Scope:** Volume I (Master Architecture and Implementation Blueprint v2.1), Volume II (Complete POC Data Specification, 11-account environment v1.0), Volume III (Source and Research Register v1.0), audited against the actual state of the `btx-omni-prospect` repository as of this date.
**Method:** Full read of all three planning volumes; direct inspection of the repository (git history, schema, domain modules, migrations, tests, CI config); a live backend test run (`uv run pytest`) and frontend typecheck/lint/build.

---

## Bottom line

The plan is viable, and it is a genuinely well-engineered plan — better disciplined than most solo-founder architecture docs. But "viable" needs a qualifier: viable as a technical program, not yet viable as a *funded, scheduled* program. There is no timeline, no effort estimate, and no sequencing of the thirteen phases against your actual capacity (a full-time consulting job plus one part-time non-coding hire). That is the real gap, not the architecture.

The second thing worth saying plainly: a meaningful share of what Volume I frames as "must build" already exists in the codebase, in working, tested form. The documents know this — there's a self-correcting appendix in Volume I that says so explicitly — but the phase plan itself (Phases 0–12) is still written largely as if starting from a thin fixture-era system. If you hand Phase 1's Codex prompt to an agent without re-grounding it in current schema state first, you risk paying to rebuild things that already pass 295 tests.

## What's actually in the repository right now

This matters because the blueprint's credibility, and my assessment of it, both rest on how accurately it describes the starting point.

I ran the actual checks rather than trusting the docs:

- **Schema:** 21 Alembic migrations, 47 tables. Critically, the tables Volume I Section 3 calls the "permanent center of the backend" and marks as requiring mandatory schema reorganization — `programs`, `component_classes`, `bu_capabilities`, `btx_facilities`, `commercial_contexts`, `monthly_commercial_history`, `paperless_accounts`, `commercial_quotes`, `orders`, `account_relationship_edges`, `crm_companies`, `crm_contacts`, `crm_deals`, `crm_activities` — **already exist as migrated tables**, not just domain dataclasses. This is a big change from the August 17 internal audit, which correctly flagged all of these as missing. Someone (you, with Codex) closed essentially the entire schema gap list from that audit in the three weeks since.
- **Product surfaces:** Today, Accounts, Intelligence, Map, Actions, Monitor are implemented, plus a governed Omni assistant drawer. A relationship graph view shipped (Phase 23 in your existing numbering), governed explanations and technical decomposition matching shipped (Phase 24), and monitor collection has a real multi-source pipeline (SAM.gov, USAspending, SEC EDGAR, FDA, NASA, Federal Register, DoD, Commerce).

Every commercial fact in the running system today is SAMPLE data built in `providers/sample/environment.py` (recently reshaped into `lake_sample/`, `paperless_sample/`, `hubspot_sample/` loaders per your own August reconciliation work) — none of it touches a real BTX system, and none of the new Volume I phases actually schedule building that connection. More on this below.

So: the codebase is not a stub, and it is not neglected. It's an actively and carefully developed system with real test discipline. The planning documents, however, are calibrated against an earlier, thinner version of it.

## Assessment of the three documents themselves

**Volume I (architecture)** is the strongest of the three as a piece of engineering writing. The decision legend (DECIDED / CALIBRATION DEFAULT / REQUIRED RESEARCH / REQUIRED INPUT / DEFERRED) applied consistently across thirteen phases, each with an owned scope, required inputs, backend changes, verification list, migration-and-removal step, and an explicit exit gate, is a real discipline most teams don't have even with a dedicated architect. The "three truth layers" model (sources → evidence → canonical graph → projections) and the refusal to let any surface compute its own truth are sound and match what's already partly built. The self-aware appendix — "Implementation chats must inspect Git before following stale rebuild language" — is the single best sentence in the document; it's rare to see a planning doc pre-empt its own staleness. It just doesn't go far enough: it names the finding but doesn't renumber or re-scope the phases in light of it.

**Volume II (data spec)** is executable rather than aspirational, which is its main virtue: eleven fully worked accounts with twelve months of commercial history, RFQ/quote/order chains, and a scored worksheet, all traceable to a stated source (Jamie workbook, POC-simulated Prism, POC-simulated Paperless). This is the right shape for handing to a code-generation agent. Its weakness is that the eleven accounts are templated closely enough to be visibly formulaic — the RFQ date cadence (2026-03-05, 04-08, 05-11, 06-14, 07-17, 08-20), the lead-time progression (25, 40, 55, 70, 85, 100 days), and the revenue-trend shapes repeat nearly identically across all eleven accounts with only the dollar magnitudes changed. That's fine as wireframe data for building UI and scoring logic against, but if this dataset is ever shown to Alan, Jamie, or the CSO as "this is what real depth looks like," the repetition will read as synthetic in about thirty seconds, which undercuts exactly the credibility this whole rebuild is trying to establish.

**Volume III (source register)** is the most operationally honest of the three: it states plainly what's USED, REFERENCE-only, REQUIRED, or PROHIBITED, and lists nine concrete missing documents/decisions (Prism field dictionary, Paperless field dictionary, HubSpot POC portal schema, BTX BU capability evidence pack, approved market taxonomy, public source policy, contact provider decision, relationship edge policy, memory/privacy policy) each pinned to the phase that's blocked without it. That's the right instinct — most plans hide their unknowns; this one inventories them. The gap is that several of these required inputs (Prism schema, Paperless schema, BTX BU capability evidence) depend on Alan and BTX providing access or documentation on a timeline you don't control, and nothing in the plan treats "waiting on Alan" as a risk with a fallback, just as a phase gate.

## Is the plan technically viable?

Yes, with more confidence than most plans get from me, because you have three weeks of git history as direct evidence the team (you plus AI coding agents) can execute against a document like this at real quality — tests written, migrations clean, phases actually shipped and merged. This isn't a bet on unproven execution capacity; it's a plan written by the same process that already produced the current, passing-tests codebase.

The technical risks that are real:

**1. Re-litigating what's already built.** Phase 1 ("Canonical commercial graph and migrations") is written as if the canonical tables don't exist. They do. If you run that phase's Codex prompt without first pointing it at current `persistence/models.py`, best case it wastes a cycle rediscovering what's there; worst case it "migrates" a working, tested table into a renamed or restructured one and you inherit real migration risk (data loss, broken foreign keys) for zero functional gain. Before starting Phase 0, have an agent produce a short delta doc: for each of the fourteen entities in Volume I Section 3, current-schema status (exists / partial / missing), and only scope Phase 1 work against the gaps.

**2. Phase numbering collision.** Your repository already has `docs/product/PHASE_20` through `PHASE_24`. The new blueprint restarts at Phase 0. Six months from now, "Phase 3" is ambiguous between two real, different bodies of work. Rename the new sequence (e.g., "Rebuild Phase 0–12" or "Canon Phase 0–12") before you generate the per-phase implementation PDFs Volume I promises as the next deliverable.

**3. The plan never schedules the thing that actually closes the HubSpot gap.** Read the thirteen phases again with this question in mind: which phase makes Omni show *real* BTX revenue, *real* BTX contacts, or *real* BTX deals? None of them. Phases 0–9 deepen the canonical model and the SAMPLE environment. Phase 10 is HubSpot write-back — but explicitly scoped against "the personal POC HubSpot account," not BTX's. Phase 12 lists "connected environment decisions" as a *required input*, not an owned deliverable. So the honest read is: executing all thirteen phases perfectly gets you a more architecturally correct, better-tested simulation. It does not, by itself, get you a system running on BTX's actual data. That's a fourteenth phase this document doesn't contain, and it's the one gated entirely on things outside your control (Alan's schema, BTX legal/IT approval, GCP environment access). Say this explicitly to whoever is deciding between this and HubSpot: the rebuild makes the simulation more convincing, but "convincing simulation" and "connected to real BTX systems" are different milestones, and only the second one matters to a skeptical CSO.

**4. No cost or time budget anywhere in 148 pages.** Thirteen phases, each with multiple owned subsystems, new tables, and a dedicated verification suite, is realistically six months to well over a year of focused engineering time even at the pace this repo has demonstrated (roughly five product phases in three weeks, but those were narrower in scope than "canonical commercial graph" or "Omni orchestration and memory"). You're doing this around a full-time healthcare consulting job and psychiatric-aide work, with one junior hire doing non-coding tasks. Nothing in the plan sequences the phases against that reality, and there's no way for BTX leadership to know from this document whether "closing the gap with HubSpot" means two months or two years. That absence is the single biggest thing missing from an otherwise disciplined plan, and it's the thing a CSO will ask about first.

## Is it viable as an argument against HubSpot?

This is worth separating from the engineering question, because it's the one that actually determines whether this project continues.

Volume I's own "Competitive position" section gets this half-right: it explicitly refuses to claim superiority before testing and frames the win condition as passing objective BTX-specific journeys, not matching a feature checklist. That's the right instinct and it's honestly stated.

But the plan — and by extension the case you'd make to the CSO — is implicitly arguing "Omni vs. HubSpot" when the more defensible and more accurate framing is "Omni feeds HubSpot." HubSpot is a CRM system of record: pipeline management, activity logging, permissioning, mobile access, an admin console a non-technical ops person can configure, vendor support, and an integrations marketplace. Nothing in these three documents proposes Omni replace that. What Omni actually is, based on everything I've read and everything in the running code, is a commercial-intelligence and scoring layer that synthesizes public signals, internal commercial history, capability matching, and a relationship graph into evidence-backed opportunity and risk calls — the thing HubSpot has no ability to do at all, generic or enterprise-tier. Phase 10's HubSpot write-back already treats HubSpot as the CRM of record Omni writes governed proposals into, not a competitor to be replaced.

If the pitch to your CSO is "our thing versus buying HubSpot," you're arguing a comparison the plan itself doesn't actually support and will likely lose on the axes a non-technical, not-cost-sensitive executive cares about (vendor support, admin UI, employee familiarity, zero maintenance burden). If the pitch is "we use HubSpot as the CRM and Omni as the intelligence layer no CRM vendor sells," you're arguing something the current architecture already reflects and that a from-scratch enterprise buy can't replicate, because it depends on BTX-specific capability, program, and relationship data no vendor has. I'd restate the competitive framing in Volume I along these lines before this goes in front of the CSO again — it changes the conversation from "why not just buy the thing that already works" to "here's the thing no vendor sells, sitting on top of whatever CRM you choose."

## Other findings worth flagging

- **Bus factor.** Just under 10,500 lines of backend module code, 47 tables, a governed-scoring/evidence/provenance model, and a phase-chat prompting discipline that depends on very precisely worded agent instructions to avoid architectural drift. This works exactly as long as you personally hold the whole model in your head and keep writing prompts this carefully. Your junior hire is doing PowerPoints and scope docs, not code, per your own plan — so today there is exactly one person (you) who can safely extend this system. That's a normal state for a three-week-old rebuild effort and not a reason to stop, but it is a real risk to name if BTX is being asked to depend on this long-term, and it argues for investing early in the kind of onboarding doc (like `REVIEWER_GUIDE.md`, which is genuinely good) that lets a second engineer ramp quickly.
- **Infra migration is under-scoped.** The stated end state is running inside BTX's own GCP environment (for BigQuery/Prism access, likely FedRAMP-adjacent controls per your earlier audit notes), not Fly.io/Vercel. That's a nontrivial infrastructure and security project, and it appears only as a supporting detail inside Phase 9 ("Google Cloud operating pattern"), not as its own scoped phase with inputs, verification, and an exit gate the way every other phase gets. Worth its own phase card before Phase 12.
- **Volume III's missing-input list is the real critical path, not the phase numbers.** Nine required inputs are named, most of them gating on Alan/BTX. Track that list, not the phase list, as your actual schedule risk — you can execute Phases 0–2 (baseline freeze, canonical migrations, BTX ontology) without any of them, but Phase 3 onward starts needing real answers.

## Recommendation

Proceed with the plan, but do three things before generating the per-phase implementation PDFs Volume I says come next:

1. Have an agent audit current schema/module state against Volume I Section 3's entity list and Volume II's data model, and rewrite Phases 0–2 to scope only the actual remaining gaps, not a from-scratch rebuild.
2. Add a rough time/effort estimate per phase, even a coarse one, so you and BTX both know whether this is a two-month or year-long program.
3. Rewrite the competitive-position framing to "Omni as intelligence layer over HubSpot," not "Omni versus HubSpot" — it's both more accurate and a stronger argument for keeping this project alive.

None of that changes the architecture. It changes whether the next conversation with your CSO is winnable.
